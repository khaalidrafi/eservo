#+TITLE: eservo — Emacs-driven web automation
#+STARTUP: showall

eservo drives a web browser from Emacs.  Point it at Chromium/Chrome
on Linux (including =emacs -nw= on a TTY), at the Servo engine —
natively on the same Android phone, or on desktop Linux — or at an
Android device browser over adb, then:

- use small interactive commands (=M-x eservo-goto=, =eservo-snapshot=,
  =eservo-click=, ...),
- run *deterministic task scripts* with **zero AI** in the loop
  (=M-x eservo-script-run=), or
- hand the tool menu to an LLM agent: =M-x eservo-agent-brief= prints
  every command plus the live page snapshot, ready to paste into any
  web/cloud chat — the Emacs-native answer to browser-use / cua-driver.

It is pure Elisp + external child processes, plus ONE optional
collection of native code: the libeservo dynamic module (native/),
which embeds the servo engine IN the Emacs process.  No xwidgets, no
GUI libraries, no package dependencies beyond Emacs 27.1 — so the same
commands run on a Linux desktop, from a TTY, and on Android/Termux,
and every op degrades to a clear install hint when the module is
absent.

* Install

Put the repo on your =load-path= and:

#+begin_src emacs-lisp
(require 'eservo)          ; core commands + backend registry
(require 'eservo-session)  ; per-site login persistence (optional)
(require 'eservo-script)   ; deterministic scripts (optional)
#+end_src

Or with =use-package= / =:vc= to your taste.  Everything else
(=eservo-cdp.el=, =eservo-servo.el=, =eservo-adb.el=) loads on
demand when you pick a backend.

Requirements: Emacs 27.1+, and for the default backend a
Chromium/Chrome binary.  The embedded servo engine needs the libeservo
module (below).  For Android: =adb= (Termux: =pkg install
android-tools=) for the adb backend and the servo attach lane; the
separate servo-APK lane is superseded by the embedded engine (its
packaging plan, including shipping the module inside the Emacs app,
is docs/EMBEDDED-SERVO.org).

* Backends

** embedded — the servo engine INSIDE Emacs (the end state)

=M-x eservo-start C-u RET embedded= (or =(setq eservo-backend
'embedded)=).  One process: Emacs dlopens =libeservo.so=, servo runs
on a private engine thread inside Emacs, offscreen software rendering,
no separate APK, no devtools port, no localhost TCP.  Design and build
lanes: =docs/EMBEDDED-SERVO.org=; =M-x eservo-embedded-load-module=
finds the module in =~/.emacs.d/modules/= or =eservo-state-dir=/lib/=
(or set =eservo-embedded-module-file=).

Honest v0 status (kept current in the design doc): boot / goto / url /
resize work when the servo-linked module is present; screenshot, keys
and the DOM ops (snapshot/fill/click/extract/evaluate) are pin-pending
against servo 0.8 and fail with errors naming the design doc; cookies
are not exposed.  The =servo= and =cdp= backends remain the full-ops
paths today.

** cdp (default) — Chromium/Chrome DevTools Protocol

Drives a real Chromium/Chrome over its DevTools Protocol: a tiny
pure-Elisp WebSocket client (=eservo-ws.el=) talks to
=--remote-debugging-port= directly — no Node, no Selenium.

#+begin_src emacs-lisp
(setq eservo-cdp-program "chromium") ; default: first of chromium/chrome
(setq eservo-cdp-headless t)         ; nil to see the browser
#+end_src

=eservo-goto / snapshot / fill / click / keys / wait / extract /
screenshot= all work; the snapshot is a compact DOM outline with =[N]=
refs that humans and agents both read.  The browser runs with a
persistent profile under =eservo-state-dir=, so ordinary logins
survive restarts by themselves.

** servo — the Servo engine (native-engine lane)

=M-x eservo-start C-u RET servo= (or =(setq eservo-backend 'servo)=).

Drives a real Servo (the Rust web engine) through its devtools
server — the same Firefox Remote Debugging Protocol Firefox's
=about:debugging= speaks.  eservo ships a small pure-Elisp RDP
client (=eservo-rdp.el=): =length:JSON= TCP framing, no
dependencies.

Three ways up:

- *Android (native on-device)*: Emacs and the servo app share ONE
  phone — no PC, no remote host.  Install the servo nightly APK from
  https://servo.org/download, =(require 'eservo-servo)=, then =M-x
  eservo-servo-android-start=: eservo starts the servo app
  (=org.servo.servoshell=) with the =servoargs= intent extra
  =--devtools=PORT= and attaches on =127.0.0.1= automatically — the
  app's devtools server is simply the local servo.  The app is
  started through a seam (=eservo-servo-android-start-function=),
  picked automatically: the patched-Emacs primitive
  =android-start-activity= when this Emacs has it (stock Emacs
  Android does not), else plain =am start= (=termux-am= from the
  Termux/emacshell prefix, or =/system/bin/am=) — zero extra
  dependencies, the same route emacshell's own terminal command
  takes — else =adb shell am start=.  =C-u M-x
  eservo-servo-android-start= forces the adb lane (Termux: =pkg
  install android-tools=, then pair/connect wireless debugging so
  adb can reach the phone itself).  Every lane uses the component
  =org.servo.servoshell/org.servo.servoshell.MainActivity= and the
  =--es servoargs "--devtools=PORT"= extra.
- *Launch* (desktop Linux): leave =eservo-servo-port= nil; eservo
  starts =servoshell= (or =servo=) from PATH with an ephemeral
  =--devtools=PORT= and attaches.  Get servo from
  https://servo.org/download (nightly tarballs).
- *Attach to a remote servo* (desktop/LAN — NOT the Android answer):
  set =eservo-servo-port= (and =eservo-servo-host= when the server is
  another machine) to a servo already running with =--devtools=.
  This is the desktop shared-servo story; on the phone itself, use
  the native lane above.

Ops (goto, snapshot with =[N]= refs, React-safe fill, click, keys,
wait, extract, evaluate) run as JavaScript in the live page via the
console actor's =evaluateJS=, so the automation surface is the page
DOM, not accessibility-tree scraping.

Honest limits (also in =eservo-servo.el= Commentary): servo's RDP
devtools subset has no screenshots and no cookie access — those ops
are nil and surface as clear errors (which also means
=eservo-session-*= does not work on this backend); =keys= synthesizes
untrusted JS events (prefer =fill=); a live-servo smoke test against
a real nightly is still pending (the suite tests the protocol
against a faithful fake server — see =tests/test-servo.el=).

** adb — Android device browser (best effort)

What is adb FOR?  It is the bridge for the device you actually hold:
it drives the real on-device browser (including the servo app
itself — set =eservo-adb-browser-package= ="org.servo.servoshell"=)
over USB/wireless debugging from desktop Emacs, and from Termux
via =pkg install android-tools=.  It is also the automation bridge
for on-device servo when the patched-Emacs =android-start-activity=
primitive is absent: =C-u M-x eservo-servo-android-start= starts
the servo app over =adb shell am start= and attaches the servo
backend on =127.0.0.1= (servo section above).  When you need
DOM-level control of a servo instead, the servo section is the
answer — native on Android, attach on desktop/LAN.

=M-x eservo-start C-u RET adb= (or =(setq eservo-backend 'adb)=).
Opens URLs in the device browser, taps and types via =input tap= /
=input text=, reads the screen through =uiautomator dump= — a
uiautomator-based =[N]= ref snapshot, =input keyevent= keys, and
=screencap= screenshots.  Pick a device with =eservo-adb-args=
=("(\"-s\" \"SERIAL\")")=.

Honest limits (also in =eservo-adb.el= Commentary): there is no DOM on
this path, so =extract=, =evaluate=, cookie/session ops and CSS
selector waits are unsupported (clear errors, not silent wrong
behaviour); =fill= only accepts ="text=..."= selectors; typing is
IME-level, not React-safe; and Chromium web content often shows up as
one big WebView node — for real site automation prefer the cdp
backend.  Raw =(tap (X Y))= coordinates exist exactly for that case.

* On a small phone (1-3 GB RAM)

eservo itself is a few thousand lines of Elisp and adds no
dependencies — the memory bill is the *browser engine*, and the
lanes differ a lot:

| Lane | Extra RAM on the phone | Notes |
|---|---|---|
| =adb= backend | ~none (drives apps already open) | No DOM ops; the lightest lane on 2 GB devices |
| =servo= via the plain =am= lane | one servo app (~100-250 MB typical) | The recommended lane on a phone; zero setup in emacshell |
| =cdp= | a Chromium (~200-400 MB) | Fine on desktop; on 2 GB phones only for short sessions |
| =embedded= (libeservo) | servo inside the Emacs process | One heavy heap in one process; experimental v0 — not the phone answer today |

Practical notes for a 2 GB device (Redmi 8A class):

- Prefer =servo= over =cdp= on-device: servo is the lighter engine,
  and the =am= lane needs no adb pairing at all.
- Keep one backend running at a time (=eservo-stop= before
  switching); Android's low-memory killer does not distinguish
  "Emacs + servo" from bloat.
- Simple pages (logins, forms, read-only automation) are the sweet
  spot; heavy SPAs will swap on 2 GB regardless of the engine.

* Logging in once per site (chat.qwen.ai, z.ai, ...)

The intended workflow — log in once, keep the session forever:

1. =M-x eservo-session-login RET chat.qwen.ai=
   opens a *headed* browser at the site.
2. Log in like a human (password manager, 2FA, whatever).
3. =M-x eservo-session-save RET chat.qwen.ai=
   writes cookies + localStorage/sessionStorage to a 0600 file under
   =eservo-state-dir=/sessions/= (0700 dir; never inside the repo,
   never echoed).

From then on =(session-load "chat.qwen.ai")= in a script — or
=M-x eservo-session-load= — restores everything before you work.
Human credentials for *scripted form-filling* come from =auth-source=
only (=M-x eservo-credentials= reads =machine chat.qwen.ai login ...
password ...= entries from =~/.authinfo.gpg=); eservo never prints,
stores or logs them.

* Task scripting WITHOUT AI

=M-x eservo-script-run RET ~/tasks/qwen-ask.org= runs a file of steps
deterministically — the same primitives the interactive commands use,
in the same order, every time.  One sexp list:

#+begin_src emacs-lisp
((session-load "chat.qwen.ai")
 (goto "https://chat.qwen.ai")
 (fill "textarea" "Summarize this: ...")
 (keys "RET")
 (wait 6)
 (extract ".answer")
 (write "~/notes/qwen-out.txt"))
#+end_src

or the same steps one-per-line in an Org file (headings, bullets and
comments are skipped).  Steps: =goto wait sleep fill fill-secret
click keys extract screenshot session-load write echo stop=.
=(fill-secret SELECTOR SITE)= pulls the password from =auth-source=
at run time — secrets never appear in script files, step logs or the
echo area.  Results come back as an =(OP . RESULT)= alist for Elisp
callers.

See =eservo-scripts/= for runnable examples.

* Agents (the agentic-driving lane)

=M-x eservo-agent-brief= prints the full tool menu with exact command
names followed by the live snapshot (and copies it to the kill-ring).
Paste that into any web/cloud model you are prompting; it now knows
the vocabulary, sees the page, and answers with the next command to
run.  This makes *the model you are already chatting with* the driving
brain — no second model, no extra service, no browser-use
installation; the snapshot/refs vocabulary is small enough for any
competent LLM.

* Security notes

- Session files ARE credentials (cookies, storage tokens): 0600 files
  in a 0700 dir under =eservo-state-dir=.  Never commit them.
- Human credentials: =auth-source= only; eservo never writes them.
- Scripts run as your Emacs user with your credentials and are NOT
  sandboxed — only run scripts you have read (=eservo-script.el=
  Commentary says the same).
- The CDP port binds to localhost for the launched browser; still,
  treat a live debugging port as sensitive and stop the browser when
  done (=eservo-stop=).

* Development

#+begin_example
make compile   # byte-compile, warnings are errors
make test      # 82 ERT tests, all offline (stub backends)
#+end_example

=tests/run.el= loads every =tests/test-*.el=.  No test needs a
browser, a device or a network connection.

The native module has its own lanes (=.github/workflows/native.yml=):
=module= builds it offline with ZERO dependencies and loads it into a
real Emacs 31.1 (ABI smoke — must stay green); =servo= compiles the
engine glue against servo =0.8.0= (the compile pin, continue-on-error
while the API is pinned) and uploads the built =libeservo.so=.

CI Emacs comes from the upstream GNU release tarball
=(.github/actions/setup-emacs-gnu)=: the sha256 is pinned to the GNU
release announcement, so no third-party binaries enter the gates.
